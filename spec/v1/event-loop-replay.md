# Event-loop replay (proposal)

`replayEventLoopTrace` and `replay_event_loop_trace` check whether a trace's successful and failed decisions agree with a named behavior. They first check the trace shape and join it to the behavior as described in the [trace record](event-loop-trace.md). They copy foreign TypeScript values before reading them. They then start at the actor's declared initial state and evaluate each input in trace order using `algal.expr.v1` in both runtimes.

For each input, rules with the matching event type are tried in ascending transition-id order. A guard must return a boolean. Every guard, write, notification and pending expression sees the state *before* that transition. Successful writes commit together after evaluation. The verifier checks the destination event's record fields and types, the state digest and byte size, the selected rule or unmatched result, notification identities in output order, and the sum of evaluator fuel consumed. Fuel has the behavior's `maxTransitionFuel` limit per input; state size has its `maxStateBytes` limit. The trace's effect counts must remain zero. Duplicate deliveries and full-mailbox decisions do not evaluate an expression.

A notification at ordinal `i` has the SHA-256 digest of the canonical object `{parent, transition, ordinal, target, type, payload}`. `parent` is the input's `messageDigest`; `transition` names its selected rule; `target` resolves `self` to the input actor; `type` is the destination event id. Its ordinal starts at zero within the rule and must be below 64. This binds identical payloads emitted by different inputs or positions to different identities. Agent-decided, owner may revisit: this digest object specifies output identity for the proposal; it does not assert that a host delivered the notification or replace the host's saved event-key binding.

For a failed input, replay evaluates in the same rule order until the first failure, without committing the attempted writes or notifications. `fuel-exhausted` requires an evaluator fuel error; `expression-error` requires an evaluator error other than fuel exhaustion, a non-boolean guard, or a write whose evaluated value does not match the state field type. `state-overflow` requires evaluated writes that would exceed `maxStateBytes`, before notification evaluation. `output-invalid` requires a notification payload that fails the destination event schema. A selected transition is recorded only after its guard succeeds; failure in a guard has a null transition. The claimed reason, transition, evaluator fuel, unchanged state digest and byte size must match the replay. An invented failure, wrong reason, wrong rule, or wrong fuel is refused with `EVENT_LOOP_SEMANTIC`. The existing shape-only fixture claims fuel exhaustion where evaluation succeeds, so it remains a negative replay vector even after its earlier commit is repaired. Agent-decided, owner may revisit: these four reasons cover only deterministic expression and schema failures; the trace does not attest a host failure or attempted external delivery.

For `defer` and `escalate`, the accepted decision may include `pending`, a JSON value from the rule's `key` or `request` expression. The shape parser permits a missing value for older shape-only records, but replay refuses it. The parser limits a supplied value to 16,384 canonical UTF-8 bytes, 32 value levels, 1,024 list items, 256 object keys, and 65,536 UTF-8 bytes per string or key. Other outcomes reject the field. Replay evaluates the expression after the guard, writes and notifications under the same fuel limit, and compares the *value* with `pending`. It checks presence separately: `null` can be a valid value, but omission is not a witness. A wrong value or fuel is refused. A pending expression that runs out of fuel can instead yield a failed decision with no state change. Agent-decided, owner may revisit: the witness is a checked proposed request value only, not proof that a host received, approved, settled, or delivered it.

The earlier shape-only fixture contains asserted fuel and output digests, so tests construct a separate replayable variant using evaluator fuel and the notification formula. Its shape-only acceptance does not qualify the original fixture as a replay. A successful replay returns the trace digest and the existing 14-field summary; for replayed entries its fuel and output counts agree with evaluation. The returned digest and summary establish internal consistency for these offline vectors, not external delivery, a provider result, or accumulated competence.

## Status and limits

This is a subset of the P1 proposal, not the complete event-loop gate. Full validation and independent review remain outstanding. The functions do not schedule actors, check a host mailbox history beyond the trace, or run effects. `bun test src/event-loop-replay.test.ts src/event-loop-pending.test.ts` checks successful, failed and refusal examples in TypeScript; `cargo test -p algal --locked event_loop` and `bun scripts/event-loop-replay-parity.ts` check Rust and cross-runtime behavior on matching vectors.
