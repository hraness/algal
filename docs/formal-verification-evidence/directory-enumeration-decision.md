# Bounded directory traversal in Bun: decision report

Research-only, 2026-09-23. No repository changes, builds, or allocation-claim relabeling. Applied the `hraness-engineering:compare-approaches` skill. Source snapshots and hashes: `/private/tmp/algal-bounded-directory-source-evidence.json`.

## Recommendation

**Do not replace `opendir` with `Glob.scan`: both eagerly collect on the installed Bun. Advance one small header-compiled C enumeration adapter as the bounded implementation candidate, with explicit platform admission and failure, before migrating callers.** Keep the current count guards while qualification proceeds; they remain useful processed-entry controls but do not establish an allocation bound. Prefer a subsequently verified Bun `fs.Dir` implementation over a permanent private adapter if its actual implementation satisfies the same contract.

The candidate must remain independently usable from the TypeScript runtime, with no dependency on the ALGAL Rust executable and no eager fallback. A `bun:ffi`/`cc` shim adds no npm dependency or external child process, and compiles against actual platform structs rather than guessing layouts. It does add experimental Bun FFI/TinyCC and system headers to the trusted base. This is a concrete qualification recommendation, **not approval to activate it on untested platforms or a claim that every Bun-only installation already has the necessary headers**. If production-stable APIs and an otherwise bare Bun installation are both absolute requirements, no qualifying replacement has yet been established for Bun 1.3.14.

## Decision constraints and existing evidence

`AGENTS.md` requires Bun 1.3.x, zero required runtime packages, independently runnable TypeScript, bounded counts/bytes/lists, and no implicit native-to-Bun fallback. The target property is bounded application-side enumeration memory before attacker-controlled directory population can be retained, with a fixed-size host/kernel batch permitted in the documented TCB. Count every exposed name except `.` and `..` before extension, name-validity, type, or symlink filtering; stop on the first count beyond the limit. This is not an atomic snapshot or a count of deleted on-disk slots under concurrent mutation.

Installed runtime: Bun **1.3.14**, revision **0d9b296af33f2b851fcbf4df3e9ec89751734ba4**, `/Users/bg/.bun/bin/bun`, SHA-256 **e0c90ec15d33363e6b70713d56bc3b2c7585c17f40a0fe0f8fd9305901d4e233**. Runtime reflection retained in `/private/tmp/algal-phase08-directory-admission/bun-directory-runtime.json` shows both `Dir.read` and its async iterator obtain and retain `fs.readdir(...)` results before yielding. Reducing `bufferSize` or breaking the loop cannot repair that code path.

For the alternative, the exact installed revision's [Glob builtins](https://github.com/oven-sh/bun/blob/0d9b296af33f2b851fcbf4df3e9ec89751734ba4/src/js/builtins/Glob.ts#L6-L21) await an entire returned array before yielding; `scanSync` does the same synchronously. The [native API](https://github.com/oven-sh/bun/blob/0d9b296af33f2b851fcbf4df3e9ec89751734ba4/src/runtime/api/glob.zig#L163-L201) finishes the walk and converts `matchedPaths` to a JS array. The [walker](https://github.com/oven-sh/bun/blob/0d9b296af33f2b851fcbf4df3e9ec89751734ba4/src/glob/GlobWalker.zig#L1175-L1197) exhausts its internal iterator. An async iterable return type therefore does not imply bounded streaming. Glob's default file/hidden-entry filtering also fails the physical-name counting contract unless explicitly changed. These are pinned-source findings, not throughput measurements.

## Comparable options

| Option | Allocation and count contract | Operation, maintenance, and decision |
| --- | --- | --- |
| Current `fs.Dir` plus limits | Limits processed records, not initial directory allocation | Keep guards during repair. Lowest migration cost; unacceptable as final allocation proof. |
| `Bun.Glob.scan` / `scanSync`, or a `readdir` wrapper | Eager arrays/maps at the pinned revision; filter output is not physical count | Reject as a repair. Worker/child isolation alone does not change the eager algorithm. |
| Header-compiled bounded C shim via `bun:ffi` `cc` | Can stop at limit+1 and copy into a fixed caller-owned buffer; libc/FS behavior must be admitted | **Next candidate.** No package/native-kernel dependency or child custody; small source surface. Experimental FFI, compiler, headers, and supported libc/FS profiles become explicit prerequisites. In-process native defects can terminate Bun. Startup cost and event-loop blocking remain unmeasured. |
| Direct FFI to libc with TypeScript `dirent` decoding | Potentially bounded, but cannot assume every libc stream is bounded | Do not prefer: hardcoded OS/architecture/libc layouts, errno access, pointer lifetime, and unqualified paths create more maintenance and unsafe-memory exposure than the header shim. |
| Shipped dedicated helper or Node-API addon | A bounded enumerator can meet the same contract; child variant isolates native memory faults | Contingency if runtime compilation/FFI cannot be admitted. Adds per-platform artifacts and distribution/install obligations. Child requires bounded framing, deadline, exit collection, and cleanup. Addon avoids child supervision but has in-process faults. No implicit ALGAL-kernel dependency. |
| Verified upstream Bun implementation/runtime update | Clean supported API if implementation uses bounded batches and closes on all exits | Preferred long term, but neither an available fixed version nor its source/tests is established here. Requires runtime/source qualification, migration receipt, and regression controls. |

Generic `ls`/`find`, another installed language runtime, and private `process.binding` APIs are not recommended substitutes: no relevant allocation/filename/platform contract was qualified, and they add unrelated dependencies or unsupported interfaces. Avoid a speculative broad rewrite around them.

Bun's [pinned FFI documentation](https://github.com/oven-sh/bun/blob/0d9b296af33f2b851fcbf4df3e9ec89751734ba4/docs/runtime/ffi.mdx#L5-L9) calls FFI experimental, warns against production reliance, and recommends Node-API for stable native interaction. Its [pinned compiler documentation](https://github.com/oven-sh/bun/blob/0d9b296af33f2b851fcbf4df3e9ec89751734ba4/docs/runtime/c-compiler.mdx#L1-L50) describes runtime C compilation using TinyCC. These qualifications must remain visible in the decision rather than being hidden behind a TypeScript helper signature.

## Candidate evidence and remaining qualification

The independent application worker's scratch `/private/tmp/algal-phase08-directory-admission/{bounded-directory-probe.c,cc-probe.ts,cc-probe-result.json}` compiled with built-in `cc`, without explicit header/library configuration, on this macOS arm64 host. It opened one directory, copied one bounded NUL-terminated name, captured errno inside C, and closed the stream before returning: status 0, count 1, written 4, failure 0. This proves **local ABI/header feasibility only**. It does not establish Linux support, minimal-install header availability, failure behavior, or libc allocation bounds.

Two concrete libc hazards prevent immediately treating generic `opendir` as qualified:

- Apple's [published libc `opendir.c`](https://github.com/apple-oss-distributions/Libc/blob/main/gen/FreeBSD/opendir.c#L117-L203) reads/caches a whole union directory; both `opendir` and `fdopendir` enable duplicate suppression. A proposed same-FD `open` → `fstatfs` → union refusal → `fdopendir` guard avoids checking an unrelated path, but still needs admitted mount stability and source/runtime correspondence. A lower bounded primitive is an alternative if that profile is too weak. Current public source is hazard evidence, not a version match to the installed OS.
- The [glibc allocator](https://github.com/bminor/glibc/blob/master/sysdeps/unix/sysv/linux/opendir.c#L90-L104) bounds its directory buffer, but [glibc `readdir64`](https://github.com/bminor/glibc/blob/master/sysdeps/unix/sysv/linux/readdir64.c#L32-L47) deliberately treats a deleted-directory `ENOENT` as EOF. `errno = 0` around `readdir` therefore cannot alone preserve an initial-absence-only empty contract. A path/FD identity or existence check and explicit mutation assumptions, or a lower primitive, need review. These current source examples do not qualify an unspecified deployed Linux libc.

The minimum next gate is a single narrow adapter, not all callers at once:

1. Record exact Bun/OS/architecture/libc/header/compiler and admitted filesystem profile; refuse unsupported or unavailable paths without an eager fallback. Qualify at least macOS and the actual supported Linux distributions/libcs before claiming both.
2. Establish source-level finite allocation for enumeration plus fixed output, including all libc branches. Cap count, total output bytes, and filename bytes; check arithmetic before allocating/copying. Count rejected names before filtering. Preserve arbitrary filename bytes until a documented decoding/admission step; reject NUL-containing input paths.
3. Preserve typed initial-absence, other IO, and budget failures. Handle mid-enumeration failures, directory replacement/deletion, failed close, and cleanup failures explicitly; never turn an unknown/truncated scan into empty success. Do not delete foreign directories, locks, or residue while admitting them.
4. Run limit−1/limit/limit+1 fixtures containing ordinary, hidden, malformed, directory, symlink, and temporary names; all filtered names consume the physical budget. Include exact output/filename-byte bounds, repeat scans for descriptor leaks, and fault injection for open/read/close and unavailable compiler/platform. Large-directory memory measurements support, but do not replace, the source allocation argument.
5. If a child is selected, bound both pipe capture and protocol records, collect exit status after EOF, own cancellation/timeout/process cleanup, and reject incomplete output. For in-process `cc`, close the compiled library only after all calls return; close directory/FD on every branch. Synchronous IO can still stall on a hostile filesystem, so do not equate a memory bound with a wall-time bound.
6. Migrate the new directory-admission callers first after independent review; inventory older `opendir` loops in `host-state.ts`, `mailbox.ts`, `process.ts`, `host-events.ts`, `coding-jobs.ts`, `application-filesystem.ts`, and `application-quota.ts` as separate bounded follow-ups. Verification harness `readdir` uses and semantic-index listing need their own input/profile analysis, not automatic replacement.

Change the recommendation if a supported Bun primitive is demonstrated genuinely bounded, if Linux/minimal-header qualification fails, or if production policy rejects the experimental FFI TCB. Then choose a reviewed fixed Bun runtime or a dedicated shipped helper/addon with its explicit distribution contract. None of the evidence here authorizes silently weakening the allocation criterion.

## Integration decision and native wording review

Parent integration owner chose to retain the consumer-admission repairs with an explicit resource gap for this slice. No experimental runtime compilation/FFI or required native dependency is to be introduced before supported-platform qualification. This report agrees. The C adapter recommendation is for an isolated follow-up candidate only; it does not change the current runtime prerequisites.

Read-only review of the current `docs/directory-admission.md`, `spec/v1/mailbox.md`, `spec/v1/organism.md`, and `docs/formal-verification-evidence/phase08-closure.md` found that unconditional native “read_dir streams” wording has already been removed. The current environmental-assumption wording and explicit incomplete MBX-04/Phase 08 scope are appropriate. No shared edits were made by this review.

Suggested precision for a later documentation patch:

> These limits count entries yielded by the directory iterator before application filtering. The iterators omit `.` and `..`. Native consumer code does not first collect all entries, but Rust, libc, and filesystem enumeration behavior remain in the operational trusted base. The focused tests exercise ordinary local directories; they do not establish a uniform allocation bound across filesystem profiles or a complete snapshot during concurrent mutation. Propagating IO errors applies to errors the underlying iterator reports: some libc implementations treat deletion during enumeration as EOF. Any stronger completeness or initial-absence-only claim requires a qualified primitive and directory/mount-stability conditions or corresponding mutation detection.

Use “the iterators omit `.` and `..`” instead of “the OS does not enumerate `.` or `..`”: raw POSIX directory entries can contain those names, and the C candidate explicitly skips them. Do not imply that a same-FD postcheck detects every concurrent change; it can reject observed disappearance/replacement, while a stable admitted filesystem/custody profile remains a separate condition.
